# 简历评估：测试、Eval 与生产可观测性迭代方案

更新日期：2026-09-10

## 结论

当前实现适合继续联调和小流量灰度，不适合在没有额外保护的情况下直接全量上线。

- 单元测试质量约 `7/10`：核心纯函数、Schema、重要回归和 API mock 覆盖较好。
- Eval 质量约 `5/10`：框架和基线机制已经存在，但样本少、偏合成，真实质量尚未校准。
- 跨仓库集成与失败恢复约 `3/10`：缺少 Agent + PostgreSQL 集成测试，以及 Frontend → Backend → Agent 的固定 E2E。
- 可观测性已具备日志、作业表、审计表和 Langfuse 基础，但尚不能凭一个 ID 快速串起完整请求，也没有告警、自愈和事故处理手册。

因此建议采用“小流量影子运行 → 人工复核 → 扩量”的上线方式。AI 分数在完成校准前只作为排序和辅助信息，不自动淘汰候选人。

## 现有测试与 Eval 的优点

- 评分输出有严格 Schema，并覆盖证据必须来自原文、维度完整、异常输出等边界。
- 调查、归属判断、题库组装、注入防御和降级路径都有针对性测试。
- Eval runner 支持 suite、机器可读报告、基线比较；全量 `SKIP` 返回非零状态，避免环境没配置却显示通过。
- 已将知识库检索、工具选择、题库和 judge 拆成不同评估面，后续可独立扩展。
- `evaluation_job`、评分卡版本、审计记录和用量记录为回归分析提供了基本数据面。

## 当前缺口

### 合并门禁

- PR 描述中的测试数量不能代替 PR head 的 CI 结果；评审时精确提交曾出现 fixture 缺少 `resume_id` 导致的失败，本地未提交修改才修正。
- Agent CI 尚未把确定性 Eval 和 baseline regression 作为阻断门禁。
- Frontend 部署工作流只构建，不运行测试；三个 PR 当时也没有可见的 GitHub checks。

### 集成测试

目前大部分数据库和上游接口都由 mock 替代，至少应增加：

1. Agent + 真实 PostgreSQL：并发提交、重复任务、状态迁移、版本递增、事务失败、重启恢复。
2. 跨仓库契约测试：请求/响应字段、状态码、权限码、状态 `6`、错误信封。
3. 3～5 份固定脱敏简历的 E2E：触发初筛、轮询作业、评分卡、题库、重试、前端刷新。
4. 故障注入：Backend 超时、GitHub 限流、LLM 超时、PostgreSQL 短暂不可用、容器重启、题库部分失败。

### 生产风险对应的回归用例

- 必须验证 `resume_id` 与 `user_id` 的归属关系，不能信任前端同时提交的两个 ID。
- 同一 `resume_id + cycle_id` 同时只能有一个活跃作业，或明确规定幂等键与覆盖语义。
- 进程重启后，`pending/running` 作业应自动恢复；不能依赖管理员手工点 `includeStale`。
- 题库生成失败不能把整个作业无差别标成 `succeeded`；应暴露 `scorecard_status` 和 `qbank_status`，或用 `partial_succeeded`。
- Frontend 应轮询服务端 job 状态，不应以仅存于内存的 `screeningIds` 作为真源。
- 题库 UI 应保留 `anchor/evidence/path` 等原始字段，并遵守后端 `pickable`。
- Backend 生产库字段变更必须通过 Flyway migration，不能只改初始化 SQL。

## 真实数据怎么选

真实生产数据应成为主要 Eval 来源；随机搜索或爬取网络简历不应替代它。原因是线上简历才包含真实字段缺失、写法、学校/项目分布、GitHub 可达性、候选人夸大方式和系统解析噪声。网络数据的分布通常不同，标注真值也更弱。

建议把数据分成四层：

| 数据层 | 建议规模 | 用途 | 是否进 Git |
|---|---:|---|---|
| 固定黄金集 | 首批 30～50 份，逐步到 100+ | 模型/Prompt 回归门禁 | 否 |
| 每轮影子集 | 每个招聘周期分层抽样 10%～20% | 发现分布漂移和线上 badcase | 否 |
| 合成/变形集 | 每类风险 5～20 条 | 注入、夸大、缺字段、乱码、超长文本、URL 异常 | 可放脱敏文本或生成规则 |
| 公开技术样本 | 少量 | GitHub API 限流、仓库结构、fork/协作归属等工程测试 | 只存允许再分发的最小 fixture |

### 黄金集的抽样维度

首批不要只挑“内容完整、GitHub 漂亮”的简历，应覆盖：

- 无 GitHub、失效链接、私有仓库、用户名而非 URL。
- 个人原创仓库、fork、课程作业、多人协作、只有少量提交。
- 项目描述很强但证据不足、技术栈罗列、疑似夸大、时间线矛盾。
- 字段缺失、Markdown/HTML、中文英文混合、超长文本和解析异常。
- 不同部门、年级、经验水平和简历完整度。

每份样本至少由两名评审独立标注，分歧由第三人裁决。标签应包括：维度分数区间、证据位置、是否应 hard-zero、GitHub 归属判断、题目是否可回答/有区分度，以及允许的降级行为。不要只保存一个“总分”。

### 使用生产简历的边界

- 在报名/隐私说明中明确：简历会用于 AI 辅助初筛、质量评估和系统改进；说明用途、保留期、访问范围和人工复核机制。若从“本次招聘”扩展到训练通用模型，应重新评估处理依据，不能默认沿用原用途。
- 原始简历与 Eval 数据集分离。Eval 使用不可逆的样本 ID，删除姓名、电话、邮箱、学号、精确住址、头像、身份证件等无关字段。
- 黄金集存放在加密、受访问控制且有审计的对象存储或数据库，不进入 Git、CI artifact、普通日志或公开 Langfuse 项目。
- 设定保留期和删除流程；Shadow 原始样本建议周期结束后 30～90 天内删除或重新授权，Gold 集至少每 6 个月复核必要性。候选人撤回或招聘周期结束后，根据声明和制度执行删除或进一步匿名化。
- 评审员只能看到完成判断所必需的数据；导出、下载和查看黄金集均记录审计。
- Eval 报告只输出聚合指标和匿名样本 ID，badcase 页面按权限临时读取原文。
- 如果真实内容会发送给第三方模型，应先确认供应商是否用于训练、保存期限、删除机制和数据处理位置；涉及境外提供时另行完成相应评估与告知。

### 网络搜索与爬取的定位

不建议抓取公开简历作为主数据集。“公开可见”不等于可以无限制收集和二次用于招聘判断，而且很难得到可靠的人类真值。

网络数据只适合以下补充用途：

- 使用明确允许再分发的数据集或自行合成文本，构造边界与攻击样本。
- 对候选人主动填写的 GitHub 地址，在已告知用途内通过 GitHub 官方 API 获取最小必要信息。
- 用自建测试账号和仓库验证 fork、协作、限流、删除、私有化等场景。

不要批量搜索候选人的其他账号，也不要将未由候选人提供的外部个人信息拼接进评分。GitHub 原始响应应限时缓存，Eval 固化的是必要的派生证据和版本信息，而非长期镜像整套公开档案。

## 建议的 Eval 指标

### 评分卡

- 与人工标签的 Spearman 相关性、分档准确率、平均绝对误差。
- hard-zero 的 precision/recall，优先控制误杀率。
- 证据引用正确率、无证据断言率、维度缺失率。
- 同一输入多次运行的一致性，以及 Prompt/模型版本间漂移。

### GitHub 调查与题库

- 仓库归属 precision/recall，尤其是 fork 与多人协作。
- 题目证据可定位率、可回答率、重复率、项目归属准确率。
- 正常降级率、错误降级率和外部 API 限流下的成功率。

### 运行质量

- 单份简历总延迟的 p50/p95/p99。
- 模型输入/输出 token、GitHub 请求数、单份成本。
- 完成率、失败率、部分成功率、重试率、僵任务数。
- 不同部门、经验水平和简历完整度上的指标切片；样本不足时只观察，不贸然得出公平性结论。

模型 Eval 不应每天直接阻断生产发布。确定性测试与小型固定集进 PR 门禁；带真实模型的完整黄金集定时运行或在模型/Prompt 变更时运行，并由负责人审批基线变化。

## 日志与可观测性现状

已有能力：

- Agent stdout 和 `10 MB × 5` 本地轮转文件，生产 compose 挂载到宿主机。
- `evaluation_job` 保存状态、尝试次数、错误摘要、评分卡版本和时间。
- `agent_conversation_log` 保存 token/耗时等运营数据，`agent_audit_log` 保存关键动作。
- Langfuse 可记录模型 trace，且已有 trace ID 基础设施。
- Backend 有控制台和 30 天文件日志，并暴露 health 与 Prometheus actuator。

但当前只能满足“有人登录服务器手工查日志”的基本排障，不能满足快速定位：

- Python 和 Java 都是非结构化文本日志，缺少统一的 `request_id/trace_id/job_id/resume_id/cycle_id/model_version/prompt_version/deploy_version`。
- Backend 代理没有把关联 ID 传给 Agent，也没有记录上游耗时、状态码和超时类别。
- `_spawn()` 的 done callback 只丢弃任务引用，没有读取并记录未捕获异常。
- 题库失败被 warning 吞掉，job 仍是 succeeded；管理员无法从状态面发现部分失败。
- 失败只保留 500 字符错误文本，没有阶段、错误码、是否可重试和上游请求标识。
- 僵任务恢复依赖人工调用；没有 worker heartbeat、lease 或启动扫描。
- `/health` 在 PostgreSQL 未就绪时仍返回 HTTP 200，仅 body 为 `degraded`，Docker healthcheck 因此会判健康。
- Compose 的 `restart: unless-stopped` 不会仅因容器进入 `unhealthy` 自动重启。
- 本地轮转日志容量较小且没有集中检索、告警或可靠留存；容器 stdout 与文件还可能产生重复数据。
- Frontend 主要使用 `console.*`，没有错误采集、release 版本或 source map 关联。
- 没有针对初筛链路的 dashboard、SLO、报警规则和 runbook。
- Backend 生产配置开启 Hibernate SQL DEBUG/TRACE，既增加噪声与成本，也可能暴露业务数据，生产应关闭。

## 上线前最小可观测性门槛

### P0：上线前完成

1. 每次触发生成 `request_id`，Backend 透传；每个 job 的所有日志固定带 `job_id/resume_id/cycle_id/trace_id`。
2. 给 job 增加阶段与结构化错误：`fetch_resume/scoring/github/qbank/persist/status_sync`、`error_code`、`retryable`。
3. 修复后台任务异常回收；任何未捕获异常必须打 ERROR，并尽力把 job 标成 failed。
4. 区分评分成功与题库成功，至少在队列 API 明确暴露部分失败。
5. readiness 在关键依赖不可用时返回非 2xx；另保留只检查进程的 liveness。
6. 服务启动自动扫描并恢复过期 job；同时阻止同一候选同一周期重复活跃任务。
7. 接入集中日志或至少确认宿主机日志采集和保留策略，建立失败率、僵任务数、p95 延迟告警。
8. 关闭生产 Hibernate SQL DEBUG/TRACE，并检查所有日志不记录简历正文、Authorization、GitHub token 和模型密钥。

### P1：首轮小流量期间完成

1. 为 Frontend 接入错误采集，携带 release、页面、request ID；source map 私有上传。
2. 建立初筛 dashboard：吞吐、阶段耗时、成功/部分成功/失败、重试、成本和外部依赖错误。
3. 写一页 runbook：如何从候选人/周期查 job，如何查 trace，如何安全重试，如何回滚版本，如何处理状态 6 卡住。
4. 保存 `git_sha/image_tag/model/prompt/schema` 版本，确保每个结果可复现和可归因。
5. 上线 badcase 一键进入脱敏待标注队列，经人工确认后才能加入黄金集。

## 推荐上线顺序

1. 先修已发现的 P0 生产风险和健康检查语义，补 3～5 份固定 E2E。
2. 对首批真实简历做影子评估，只向少数评审展示，不影响候选状态和淘汰结果。
3. 人工双标首批 20～50 份黄金集，校准阈值、judge 和 hard-zero 误杀率。
4. 达到约定指标后扩大到全部简历，但继续保持人工最终决定。
5. 每轮复盘失败、部分成功和人工驳回案例，将确认后的 badcase 纳入回归集。

## 上线验收建议

一次验收应能从管理页看到某个失败 job，并在五分钟内回答：

- 哪个版本、谁、何时触发了哪份简历？
- 卡在哪个阶段，失败属于哪个错误码，是否可安全重试？
- Backend、Agent、LLM/GitHub 和 PostgreSQL 各自耗时与返回是什么？
- 简历状态是否已恢复，评分卡与题库是否分别成功？
- 是否影响其他候选人，需要回滚还是只重试单个 job？

如果必须登录多台机器、凭时间戳猜测日志或查看候选人原始 PII 才能回答，就还没有达到可快速定位的标准。

## 数据治理依据

本文的数据建议参考以下一手资料，不替代正式法律意见：

- [中国人大网：《中华人民共和国个人信息保护法》](https://www.npc.gov.cn/npc/c2/c30834/202108/t20210820_313088.html)：目的限定、最小必要、自动化决策、保存期限、去标识化/匿名化、安全措施与个人权利。
- [国家互联网信息办公室：《个人信息保护合规审计管理办法》及指引](https://www.cac.gov.cn/2025-02/14/c_1741233507681519.htm)：自动化决策、影响评估、保留期限和合规审计要求。
- [GitHub Acceptable Use Policies](https://docs.github.com/en/site-policy/acceptable-use-policies/github-acceptable-use-policies)：个人信息收集、授权用途、安全与删除请求等边界。
- [GitHub REST API rate limits](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)：使用官方 API 时的认证、限流和重试约束。
